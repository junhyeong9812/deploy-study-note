# requirement-spec — 관측 서버: 로그 수집·저장·조회

> 2026-11-21. 대상 repo: `observe`(신규, 공개) · `ci-cd`(배포 대상에 observe 추가) · `alert`(감시 대상에 observe 추가).
> 로드맵(`NEXT.md`) 운영 관측 묶음 ②. 앞: 알림 서버(11-21 적용). 뒤: 어드민 뼈대 → 자원 지표 → 방문 추적.

## 0. 요구사항 원문
- 사용자(11-19~20): "로그를 중앙 관제" · 구조 합의 — Kotlin, 관측 서버와 알림 서버 둘, 관측 서버는 PostgreSQL, 서버 간 메시지 통로는 Redis Stream(로그는 기존 `logs`), 로그 보관 30일, 어드민 화면이 관측 서버를 직접 조회.
- 사용자(11-21): "알림 테스트는 후순위로 미루고 다음 진행".
- 선택 답(11-21): 배치 = `.158` / 범위 = 수집·저장·조회 API만(오류 급증 알림은 실제 분포를 본 뒤 별도) / 수집 대상 = 스트림 로그만 / 검색 = 부분 일치.
- 관측 신호(11-21 실측): `logs` 스트림에 읽는 쪽이 없어 131만 건이 지나가고 최근 1만 건(약 9시간치)만 남는다 · 한 줄 형식 `<요청ID>:<서비스>:<내용>`이 최근 1만 건 중 1만 건에서 분해됨 · 서비스 분포 front 57%·backend 41%·llm-wrapper·ci-master·ci-agent 3대 · 레벨 info 99.1%·warning 0.6%·error 0.3% · 하루 약 2만 5천 건(30일 약 75만 건) · Redis 7.4, 디스크 저장 없음.

## ① 목표·대상
네 서비스가 이미 보내고 있는 요청 단위 로그를 **30일 동안 찾아볼 수 있게** 한다. "이 요청ID에 무슨 일이 있었나", "어제 저녁 backend의 error는", "이 오류 문구가 언제부터 났나"에 API 한 번으로 답한다. 화면은 다음 작업(어드민)이 이 API를 쓴다.

## ② 경계·불변식
- **수집**: `.158` Redis의 `logs` 스트림을 소비자 그룹으로 읽는다. 저장에 성공한 뒤에만 확인(ack)한다 — 관측 서버가 죽었다 살아나면 확인하지 못한 것부터 다시 받는다. 같은 항목을 두 번 받아도 한 번만 저장된다(스트림 ID가 기본 키).
- **유실 범위(받아들이는 것)**: **전제 = 수집이 스트림이 버티는 시간(상한 약 1만 건, 평소 약 9시간치)보다 오래 멈추지 않는다.** 수집이 멈추는 경우는 관측 서버가 꺼졌을 때와, 떠 있어도 DB에 저장하지 못할 때(DB 불통·디스크 가득) 둘 다다. 전제 안에서는 잃지 않는다. 전제가 깨지면 그 사이 상한을 넘어 밀려난 로그를 잃는다 — 이 상태는 헬스 503으로 알림 서버가 잡고, 밀려나 잃은 건수는 경고 로그에 남는다. Redis가 재시작하면 스트림에 남아 있던 미수집분도 잃는다. *(11-21 리뷰 반영·사용자 확인 — 원문은 "꺼진 사이"만 적었다)*
- **발신 쪽 무변경**: 네 서비스의 로거·형식·스트림 상한을 바꾸지 않는다. 관측 서버가 한 줄을 요청ID·서비스·내용으로 나눈다. 나눌 수 없는 줄은 버리지 않고 서비스 `unknown`·원문 그대로 저장한다.
- **시각**: 로그 시각은 스트림 ID의 밀리초(Redis가 받은 시각)다.
- **저장**: PostgreSQL(관측 서버 compose 안, 호스트 볼륨, LAN에 열지 않음). 30일 지난 행은 매일 지운다. DB 계정·비밀번호는 서버 `.env`에만.
- **조회 API**(서버 간 비밀값 `X-Observe-Secret`, LAN 포트 17000):
  - `GET /logs` — 기간(from·to)·서비스·레벨·요청ID·내용 부분 일치(q, 2자 이상)로 거르고 최신순, 한 번에 최대 500건, 이어 보기(커서). 기간을 안 주면 최근 1시간.
  - `GET /logs/stats` — 기간 안의 서비스·레벨별 건수(시간 단위 묶음). 어드민 화면의 추이와, 나중에 오류 급증 기준을 정할 근거.
  - `GET /health`(비밀값 없음) — 수집이 살아 있는가: 마지막으로 저장한 로그의 시각, 아직 확인하지 못한 건수. DB나 Redis에 닿지 못하면 503.
- **독립성**: 관측 서버가 죽어도 네 서비스의 요청 처리와 로그 발신은 영향이 없다(지금도 읽는 쪽이 없다). 조회가 무거워도 수집이 밀리지 않는다(수집과 조회의 DB 연결을 나눈다).
- **배포**: ci-cd 파이프라인(test 단계·blue/green), `.158`. 두 자리가 겹치는 동안에는 소비자 그룹이 항목을 한쪽에만 주고, 기본 키가 중복 저장을 막는다 — 자리별 활성 판정은 두지 않는다. 30일 삭제가 두 자리에서 함께 돌아도 결과가 같다.
- **감시**: 알림 서버의 감시 대상에 관측 서버 `/health`를 더한다.

## ③ 기준소스
네 서비스의 로거(backend `shared/infra/RequestLog.kt` · ci-cd `internal/shared/logger.go` · front `src/shared/lib/logger.ts` · llm `wrapper/src/app/logger.py` — 스트림 이름 `logs`, 필드 `level`·`line`, `MAXLEN ~ 10000`) · 실측(11-21: 위 관측 신호, `.158` 여유 메모리 10GB·디스크 143GB, 포트 17000~17002·5432 비어 있음) · 알림 서버 repo의 구성(Kotlin·Spring Boot 4.1.1·Java 21, compose 두 자리 + nginx, Dockerfile test 단계, 워크플로) · ci-cd `internal/master/master.go`·`internal/agent/agent.go`의 배포 대상 목록 · alert `src/main/resources/monitors.yml`.

## ④ 금지영역
네 서비스의 로거·로그 형식 변경 · 컨테이너 표준 출력·nginx 접근 로그·ES·Ollama 로그 수집 · 오류 급증 알림(관측 → 알림 사건) · 어드민 화면 · 자원 지표·방문 기록 · Redis 설정 변경(디스크 저장·메모리 상한) · 기존 Elasticsearch에 로그 색인 · 관측 서버 DB를 다른 서비스가 직접 읽기(API로만) · PostgreSQL 포트의 LAN 노출.

## ⑤ 검증 방법
- 단위(observe): 한 줄 분해(정상·콜론이 든 내용·나눌 수 없는 줄·빈 줄) · 스트림 ID → 시각 · 저장 성공 뒤에만 ack(저장 실패 시 ack 안 함) · 조회 조건 검증(기간 역전·q 1자·limit 상한·잘못된 커서 422) · 인증 없는 조회 401 · 헬스 판정.
- 실제 엔진(observe, 로컬 — 실제 PostgreSQL·Redis 컨테이너): 같은 항목 두 번 저장 → 1행 · 재시작 뒤 미확인분 재수신 · 소비자 둘이 동시에 읽어도 누락·중복 0(넣은 건수 = 저장된 건수) · 부분 일치 검색이 인덱스를 타는지(75만 행 규모로 채운 뒤 실행 계획과 시간) · 커서 이어 보기에서 누락·중복 0 · 30일 삭제.
  - 한계: 이 테스트는 Docker 빌드의 test 단계에서는 돌지 못한다(빌드 안에서 DB를 띄울 수 없다). 로컬 실행 스크립트로 두고, 파이프라인의 test 단계는 단위만 돈다 — log에 기록.
- 실행(서버): ① 배치 뒤 스트림의 밀린 1만 건이 들어오고 `/health`의 미확인이 0으로 ② 사이트에서 문서를 하나 열고 그 요청ID로 조회해 front·backend 줄이 함께 나오는지 ③ 관측 서버를 5분 내렸다 올려 그 사이 로그가 빠짐없이 들어왔는지(스트림 ID 연속성) ④ 파이프라인 배포(두 자리 교대) 중 중복·누락 0 ⑤ 알림 서버가 관측 서버 정지를 DOWN으로 잡는지.
- 반증: 관측 서버가 느리거나 죽었을 때 네 서비스의 응답 시간이 변하나(변하면 안 된다)? 내용에 콜론·줄바꿈·아주 긴 줄이 오면? DB 디스크가 차면 수집은 어떻게 되고 어디에 남나? 조회로 큰 기간을 요청하면 수집이 밀리나?
- 리뷰: 중간 — 듀얼 1패스 + post-fix 재점검.

## ⑥ stakes: 중간
새 서비스 + 새 DB(외부 큐 소비·ack·재시도·보관 삭제) + 두 repo의 작은 변경. 기존 데이터·기존 서비스 동작은 바꾸지 않는다. 관측 서버가 잘못돼도 서비스에는 영향이 없고 repo별 revert로 되돌린다. 주된 위험은 조용한 누락(수집이 멈췄는데 모름)과 삭제 작업의 범위 오류 — 헬스의 미확인 건수와 알림 서버 감시, 삭제의 기준 시각 테스트로 막는다.

## load-bearing 가정 (착수 직후 실증)
1. Spring Data Redis로 소비자 그룹 읽기(블로킹)·ack·미확인분 재수신이 Spring Boot 4.1.1에서 기대대로 동작한다 — 안 되면 수집 방식을 다시 정한다.
2. 75만 행에서 내용 부분 일치 검색이 trigram 인덱스로 1초 안에 끝난다 — 안 되면 검색 범위(기간 필수 등)를 좁힌다. → **판정(11-21 실측·사용자 확인)**: 3자 이상은 1초 안(최대 0.25초). 2자 검색어는 trigram 으로 좁힐 수 없어 드문 말이면 전체를 훑는다(0.45~1.0초) — 2자를 허용하고 1초 안팎을 받아들인다(조회는 10초에서 끊기고 수집과 연결이 나뉘어 있다).
