## 1. 목표 · 대상 (①)

집 서버 세 대(`.9` · `.158` · `.164`)의 자원 사용을 30초마다 모아 30일 보관하고, 임계값을 넘으면 알리고, 어드민에서 그래프로 본다.

- **모으는 곳**: ci-cd agent(서버마다 하나 — `study-note-deploy-system-ci-cd`).
- **보관·판정하는 곳**: 관측 서버(`study-note-deploy-system-observe`, `.158`).
- **알리는 곳**: 알림 서버(`study-note-deploy-system-alert`) — 지금 있는 `POST /events` 로 받는다. 알림 서버는 고치지 않는다.
- **보는 곳**: 어드민(`study-note-deploy-system-admin`) — 새 화면 "서버 자원", "상태 한눈에"의 요약, 연관 로그의 자원 구역.

## 2. 경계 · 불변식 (②)

### 2.1 무엇을 모으나 (30초마다, 서버별)

| 갈래 | 값 |
|---|---|
| 서버 전체 | CPU 사용률(%) · 부하(1분) · 메모리 사용/전체 · 루트 디스크 사용/전체 · 네트워크 초당 송신·수신(바이트) · 디스크 초당 읽기·쓰기(바이트) |
| 컨테이너별 | CPU 사용률(%, 코어 하나 = 100) · 메모리 사용 · 재시작 횟수(누적) · 상태(running 등) |
| GPU(있는 서버만 — `.158` · `.164`) | 사용률(%) · 메모리 사용/전체 · 온도 |

- **이 프로젝트의 컨테이너만** 모은다 — compose 프로젝트 이름이 `study-note-deploy-system-` 로 시작하는 것. 그 밖의 컨테이너는 이름도 값도 싣지 않는다(서버 전체 값에는 자연히 포함된다).
- 접속 주소·환경 변수·명령줄·컨테이너 안의 파일은 읽지 않는다. 컨테이너 이름과 숫자만.

### 2.2 흐름

```
agent(서버마다, 30초) ──XADD──▶ Redis 스트림 metrics(.158) ──▶ 관측 서버 ──▶ PostgreSQL
                                                               │
                                                               ├─ 임계값 판정 ──POST /events──▶ 알림 서버
                                                               └─ 조회 API ◀── 어드민
```

- 통로는 로그와 같은 Redis(스트림만 다르다 — `metrics`). agent 는 이미 로그를 같은 방식으로 보낸다.
- 한 번의 수집 = 스트림 항목 하나(그 서버의 서버 전체 · 컨테이너들 · GPU 를 한 묶음으로). 수집 시각은 agent 의 시계.

### 2.3 불변식

- **수집이 배포를 막지 않는다**: 수집은 배포 잠금(`busy`)을 잡지 않는 별도 흐름이다. 한 번의 수집은 전체 10초 안에 끝나거나 버려지고, 앞 수집이 안 끝났으면 다음 수집을 겹쳐 시작하지 않는다. 수집의 어떤 실패도 agent 를 죽이지 않고 배포 경로의 동작을 바꾸지 않는다.
- **수집은 읽기만**: 호스트에 쓰지 않는다. 도커에는 조회만 보낸다 — 단 하나의 예외는 GPU 값을 읽으려고 **지정된 컨테이너 하나 안에서 `nvidia-smi` 를 실행**하는 것이다(2.5).
- **보내지 못해도 조용히 사라지지 않는다**: Redis 에 넣지 못한 횟수를 agent 가 세어 로그에 남기고(연속 실패가 이어지면 1줄), 관측 서버는 서버별 마지막 수신 시각을 헬스와 조회 응답에 낸다. 지표가 3분 넘게 안 들어오는 서버는 그 자체가 알림 대상이다(2.4).
- **한 서버의 문제가 다른 서버의 지표를 막지 않는다**: 관측 서버는 항목 하나가 깨져 있으면 그 항목만 버리고(건수를 헬스에 낸다) 나머지를 저장한다. 저장 뒤에만 스트림에 확인한다(로그와 같은 규칙).
- **보관**: 원본(30초) 7일, 5분 평균(평균과 최댓값) 30일. 5분 평균은 원본을 지우기 전에 만들어져 있어야 한다 — 만들지 못한 구간의 원본은 지우지 않는다.
- **조회는 상한을 둔다**: 기간 최대 31일, 한 계열에 점 최대 500개(넘으면 관측 서버가 구간을 넓혀 평균을 낸다 — 응답에 실제 간격을 적는다). 입력이 틀리면 422.
- **인증**: 관측 서버의 새 경로는 전부 `X-Observe-Secret`. 어드민은 지금처럼 세션을 확인한 뒤에만 부르고, 한 구역이 실패해도 다른 구역은 보인다.
- **기존 동작 무변경**: 로그 수집·조회, 로그인 시도 기록, 배포 경로, 알림 서버는 그대로다(특성 테스트로 고정).

### 2.4 임계값과 알림 (관측 서버가 판정)

| 규칙 | 넘음(알림) | 해소 |
|---|---|---|
| 디스크 사용률 | 85% 이상 → 경고 · 95% 이상 → 위험(연속 2회 관측) | 각 기준보다 3%p 아래로 연속 2회 |
| 메모리 사용률 | 90% 이상이 5분 이어짐 → 경고 | 85% 아래가 5분 이어짐 |
| CPU 사용률 | 90% 이상이 10분 이어짐 → 경고 | 80% 아래가 5분 이어짐 |
| 컨테이너 재시작 반복 | 한 컨테이너의 재시작 횟수가 10분 안에 3 이상 늘어남 → 경고 | 10분 동안 늘지 않음 |
| 지표 끊김 | 한 서버의 지표가 3분 넘게 안 들어옴 → 경고 | 다시 들어옴 |

- 넘을 때 1회, 해소될 때 1회, 계속 넘어 있으면 1시간마다 다시 알린다. 수치는 설정값(환경 변수)이고 위가 기본값이다.
- 알림은 알림 서버의 `POST /events`(`source: "observe"`, `kind: "resource_*"`, `key: "resource:<서버>:<규칙>[:<컨테이너>]"`). 해소는 다른 key(`…:resolved`)로 보낸다 — 알림 서버가 같은 key 를 10분에 한 번만 보내기 때문이다.
- 판정 상태(넘어 있는지 · 언제부터 · 마지막으로 알린 때)는 PostgreSQL 에 둔다 — 관측 서버가 재시작하거나 자리를 바꿔도 같은 알림을 다시 보내지 않고, 해소를 놓치지 않는다.
- 알림 서버에 닿지 못하면 판정 상태를 "알림 못 보냄"으로 두고 다음 판정 때 다시 보낸다(조용히 넘어가지 않는다). 지금 알림 채널 주소가 임시값이라 실제 발송은 실패로 기록된다 — 이번 작업의 확인은 알림 서버에 접수되는 것까지다.

### 2.5 GPU

agent 컨테이너에는 `nvidia-smi` 가 없다(11-24 실측). agent 는 **설정으로 지정된 컨테이너**(`.164` 는 `llm-ollama`, `.158` 은 GPU 를 쓰는 컨테이너 — 착수 때 실측으로 정한다) 안에서 `nvidia-smi` 의 조회 명령을 실행해 값을 읽는다. 설정이 없으면 GPU 는 모으지 않는다(`.9`).

- 그 컨테이너가 꺼져 있으면 GPU 값은 그 수집에서 빠진다(다른 값은 그대로) — 화면은 "GPU 값 없음"으로 보인다.
- 실행하는 것은 고정된 조회 명령 하나뿐이고, 컨테이너 이름은 설정값에서만 온다(요청 입력이 아니다).

### 2.6 어드민 화면

- **새 화면 "서버 자원"**(`/resources`): 서버 셋의 현재 값(CPU · 메모리 · 디스크 · 네트워크 · 디스크 입출력 · GPU)과 선 그래프, 기간 선택(1시간 · 24시간 · 7일 · 30일), 서버별 컨테이너 표(CPU · 메모리 · 재시작 횟수 · 상태 — 누르면 그 컨테이너의 그래프). 넘어 있는 임계값은 그 자리에 표시한다.
- 그래프는 서버에서 그린 SVG 다(차트 라이브러리 없음, 브라우저 스크립트 없음 — 지금 화면들과 같다). 색만으로 구분하지 않고 값·단위·시각 축을 글자로 낸다. 자동 갱신은 없다("새로 고침" 링크).
- **"상태 한눈에"**: 서버별 한 줄(CPU · 메모리 · 디스크 · 마지막 수신 시각)과 넘어 있는 임계값을 요약에 더한다. "서버 자원"으로 가는 링크.
- **연관 로그**: "그때 서버 상태"에 그 로그를 남긴 서비스가 있는 서버의 앞뒤 5분 자원 수치(CPU · 메모리 · 그 서비스 컨테이너의 CPU · 메모리) 구역을 더한다. 값이 없으면(보관 기간 밖 · 수집 전) "기록 없음".
- 지표가 오래된 서버(3분 넘게 안 들어옴)는 값 옆에 "N분 전 값"으로 표시한다 — 오래된 값을 지금 값처럼 보이지 않게.

## 4. 금지영역 (④)

- 알림 서버의 코드 · 감시 대상 정의 · 채널 설정(이번엔 받는 쪽으로만 쓴다).
- 배포 경로(`/deploy` · `/agent/ci` · `/agent/cd` · 자리 전환)와 조회 경로(`/deploys/git/*`)의 동작.
- 이 프로젝트가 아닌 컨테이너의 이름·값 수집, 접속 주소·환경 변수·명령줄 수집.
- Redis 의 디스크 저장 켜기(방문 추적 ⑤ 때 정한다) · 서버의 sudo 가 필요한 일(옛 `metrics-agent` 정리는 사용자가 한다).
- 통신 지도 · 요청 추적(NEXT.md ⑬) — 이번 범위가 아니다. 다만 이번에 내는 수집 길 위에 그대로 얹힐 수 있게, 스트림 항목과 관측 서버의 수집 구조를 지표 전용으로 굳히지 않는다(항목에 종류 칸을 둔다).

## 5. 검증 방법 (⑤)

- **자동**
  - ci-cd: 가짜 `/proc` 받침 파일과 가짜 도커 응답으로 값 계산(CPU 는 두 번의 차이, 초당 값은 간격으로 나눔) · 이 프로젝트가 아닌 컨테이너가 빠지는지 · 수집이 `busy` 와 무관한지 · 10초 기한과 겹침 방지 · Redis 가 죽어도 agent 와 배포가 그대로인지 · 기존 경로의 특성 테스트.
  - observe: 실제 PostgreSQL · Redis 로 도는 엔진 테스트 — 저장 뒤 확인 · 깨진 항목 버리기 · 5분 평균(평균·최댓값·경계 시각) · 원본 삭제가 평균이 없는 구간을 건드리지 않는지 · 조회의 점 500개 상한과 간격 · 임계값 다섯 규칙의 넘음·해소·다시 알림(가짜 시계) · 재시작 뒤 같은 알림을 다시 보내지 않는지 · 알림 서버가 죽었을 때 다시 보내는지.
  - admin: 데이터 계층(응답을 믿지 않는다 — 꼴이 다르면 해석 불가) · 그래프 SVG 의 좌표 계산(빈 계열 · 점 하나 · 값이 전부 같음 · 구멍 난 구간) · 화면 렌더 · 세션 없는 요청 거절 · 한 구역 실패 시 나머지.
- **뮤테이션**: 불변식마다 구현을 한 곳씩 망가뜨려 테스트가 깨지는지(잠금 잡기 · 필터 제거 · 저장 전 확인 · 평균 없이 원본 삭제 · 해소 생략 · 상한 제거).
- **서버**: 세 서버의 agent 를 올린 뒤 관측 서버에 서버 셋의 지표가 30초 간격으로 쌓이는지 · agent 의 CPU·메모리 부담(수집 전후 비교) · 배포 한 건이 수집과 겹쳐도 그대로 끝나는지 · 임계값을 일부러 낮춰 넘음 → 알림 서버 접수 → 되돌려 해소 접수 · 어드민 화면을 바깥 도메인에서 확인.

## 10. task 01 결과와 계약 (11-24 — 2절의 세부. 어긋나면 이 절이 우선)

### 10.1 가정 실측(세 서버, 읽기만)
- **가정 1 성립**: agent 컨테이너 안에서 `/proc/stat` 의 CPU 누적 · `/proc/meminfo` 의 `MemAvailable` · `/proc/net/dev` 의 호스트 장치(`eno1` 등 — host 네트워크) · `/proc/diskstats` 의 실제 디스크(`nvme0n1` 등) · 루트 디스크 용량이 호스트 값과 같다. 마운트를 더하지 않는다.
- **가정 2 성립**: 도커 API 의 한 번짜리 통계(`stats?stream=false&one-shot=true`)는 컨테이너 4~10개에서 25~97ms(차례로). 단 한 번짜리 응답에는 직전 표본이 없다(`precpu` 가 0) — **컨테이너 CPU 사용률은 agent 가 앞 수집의 누적 값과의 차이로 계산**한다(서버 전체 CPU 와 같은 방식).
- **가정 3 — `.164` 성립, `.158` 불성립**: `.164` `llm-ollama` 안의 `nvidia-smi` 는 74ms 에 값을 낸다. `.158` `backend-embedding` 안에서는 `Failed to initialize NVML: Unknown Error`(호스트의 `nvidia-smi` 는 정상 — GPU 메모리 4.9G 사용 중). 컨테이너를 다시 만들어야 풀리는 알려진 현상으로 보인다 — 이 작업에서 backend 를 건드리지 않는다. 따라서 `.158` 의 GPU 값은 그 컨테이너가 다시 만들어질 때까지 "값 없음"이다(2.5 의 규칙 그대로). 사용자에게 보고한다.
- compose 프로젝트 이름은 세 서버 모두 `study-note-deploy-system-<서비스>` 다. 예외 하나: `.158` 의 `claude-bridge-relay` 는 compose 프로젝트가 없다(이 프로젝트의 것) — **설정으로 이름을 더 지정할 수 있게** 한다(`METRICS_EXTRA_CONTAINERS`).

### 10.2 스트림 항목 (agent → Redis)
- 스트림 `metrics`(설정 `METRICS_STREAM`), `XADD … MAXLEN ~ 20000`. Redis 주소는 로그와 같은 `LOG_REDIS_URL`. 주소가 비면 수집 자체를 하지 않는다(시작 로그 1줄).
- 칸: `kind`(`resource` — 다른 종류가 같은 길을 쓸 수 있게) · `v`(`1`) · `server`(agent 의 `SERVER_NAME`) · `at`(수집 시각, epoch 밀리초) · `body`(JSON, 64KB 이하).
- `body`:

```json
{
  "interval_ms": 30012,
  "host": { "cpu_pct": 3.4, "load1": 0.11, "mem_total": 16000000000, "mem_used": 2100000000,
            "disk_total": 500235124736, "disk_used": 80570650624,
            "net_rx_bps": 1200, "net_tx_bps": 3400, "io_read_bps": 0, "io_write_bps": 52000 },
  "containers": [ { "name": "front-app-green", "id": "0123456789ab", "project": "study-note-deploy-system-front",
                    "cpu_pct": 0.7, "mem_used": 119000000, "restarts": 0, "state": "running" } ],
  "gpus": [ { "index": 0, "util_pct": 0, "mem_used": 9437184, "mem_total": 8589934592, "temp_c": 28 } ],
  "missing": ["gpus"]
}
```

  - 사용률·초당 값은 **앞 수집과의 차이**다. 첫 수집 · 누적 값이 줄어든 경우(재부팅·장치 초기화) · 간격이 2분을 넘은 경우에는 그 값을 `null` 로 낸다(틀린 급등을 만들지 않는다).
  - `mem_used` = 전체 − `MemAvailable`. 컨테이너의 `mem_used` 는 사용량에서 비활성 파일 캐시를 뺀 값(`docker stats` 와 같은 계산).
  - `cpu_pct`: 서버 전체는 0~100(모든 코어 평균), 컨테이너는 코어 하나 = 100.
  - `missing`: 이번 수집에서 읽지 못한 갈래 이름(`host` · `containers` · `gpus`). 읽지 못한 갈래는 빈 값으로 두고 나머지를 보낸다. GPU 설정이 없는 서버는 `gpus: []` 이고 `missing` 에 넣지 않는다.
  - 컨테이너는 최대 50개(넘으면 이름순 앞 50개 + `missing` 에 `containers_truncated`).

### 10.3 관측 서버의 조회 API (어드민이 부른다 — 전부 GET, `X-Observe-Secret`)
- `GET /metrics/latest` → `{ servers: [ { server, at, age_ms, stale(bool — 3분 초과), host{…}, containers[…], gpus[…], missing[…] } ], firing: [ { server, rule, target, severity, since, last_value } ] }`. 서버는 최근 24시간 안에 한 번이라도 지표를 보낸 것 전부.
- `GET /metrics/series?server=&scope=host|container|gpu&name=&from=&to=` → `{ server, scope, name, from, to, step_ms, source("raw"|"rollup"), points: [ { at, <값마다 avg> , <값마다 _max> } ] }`.
  - `name`: container 는 **자리 이름을 뗀 이름**(`front-app-green` → `front-app`), gpu 는 `0` 같은 번호, host 는 생략.
  - 기간 기본 1시간 · 최대 31일. 점이 500개를 넘지 않게 관측 서버가 `step_ms` 를 고른다(30초 원본 → 필요한 만큼 묶어 평균·최댓값). 7일보다 오래된 구간은 5분 평균에서 읽는다.
  - 값이 없는 구간은 점을 만들지 않는다(0 으로 채우지 않는다).
- `GET /metrics/containers?server=` → 그 서버에서 최근 24시간에 보인 컨테이너 이름 목록(자리 이름을 뗀 것)과 마지막으로 보인 시각.
- 헬스(`GET /health`)에 지표 수집의 칸을 더한다: 마지막 저장 시각 · 버린 항목 수 · 밀린 건수 · 5분 평균의 마지막 성공 시각과 실패 사유 · 임계값 판정의 마지막 시각과 못 보낸 알림 수. 지표 쪽이 실패해도 **로그 수집의 상태 낱말(`status`)은 바꾸지 않는다** — 지표용 상태 칸을 따로 둔다.

### 10.4 서비스가 있는 서버 찾기(연관 로그)
어드민은 `GET /metrics/containers` 의 결과에서 로그의 `service` 이름으로 시작하는 컨테이너(`front` → `front-app`)가 보인 서버를 고른다. 못 찾으면 그 구역은 "기록 없음".

## 11. 설계 선검증 반영 (11-24 — codex 1회. 앞 절과 어긋나면 이 절이 우선)

### 11.1 agent
- **간격은 단조 시계로 잰다**(벽시계 보정이 초당 값을 흔들지 않게). 앞 표본은 장치별 · 컨테이너 ID 별로 따로 둔다 — 기준이 바뀌었거나(새 컨테이너 · 새 장치) 누적 값이 줄었거나 간격이 2분을 넘으면 **그 값만** `null` 로 내고 기준을 새로 잡는다.
- **기한은 호출마다 전달한다**(도커 조회 · GPU 명령 · Redis 전송 각각). 겹침 방지는 "앞 수집이 실제로 끝났는가"로 판단한다 — 기한이 지났는데 안 끝난 수집이 있으면 다음 수집을 건너뛰고 건너뛴 횟수를 센다.

### 11.2 관측 서버 — 저장
- **같은 항목을 두 번 받아도 한 번만 저장한다**: 스트림 항목 ID 가 고유 키다(저장 뒤 확인 전에 죽으면 다시 받는다).
- **깨진 항목**: 꼴이 틀린 항목은 이유와 항목 ID 를 로그에 남기고 건수를 센 뒤 확인한다(다시 받지 않게). DB 가 실패한 것은 버리지 않고 확인하지 않는다(다음 바퀴에 다시).
- **시각 둘**: 측정 시각(`at` — agent 의 시계)과 수신 시각(관측 서버의 시계)을 모두 저장한다. 측정 시각이 수신 시각보다 2분 넘게 앞서 있으면(서버 시계가 빠름) 그 항목은 버리고 이유를 센다 — 미래의 값이 "최신"을 차지하지 않게. 그래프와 평균은 측정 시각으로, 끊김 판정은 수신 시각으로 한다.
- **스트림 유실(알려진 한계)**: 스트림 상한(약 2.3일분)을 넘게 관측 서버가 꺼져 있거나 Redis 가 재시작하면 그 구간의 지표는 사라진다 — 그래프에 빈 구간으로 보인다. 밀린 건수는 헬스에 낸다.

### 11.3 관측 서버 — 5분 평균과 삭제
- 5분 구간마다 값별 **평균 · 최댓값 · 표본 수**를 저장한다. 원본이 남아 있는 동안은 언제든 다시 계산할 수 있다 — 평균을 만든 뒤 그 구간에 원본이 더 들어오면(늦은 도착) 다음 바퀴에 그 구간을 다시 계산해 덮어쓴다.
- 원본 삭제는 "7일이 지났고, 그 구간의 평균이 그 구간의 마지막 원본 수신보다 뒤에 계산돼 있는" 구간만.
- 더 큰 간격으로 묶을 때는 **표본 수로 가중한 평균**과 최댓값의 최댓값을 쓴다(평균의 단순 평균을 내지 않는다).

### 11.4 관측 서버 — 임계값 판정
- **판정은 30초마다 도는 작업이 한다**(항목을 받을 때가 아니다). 그 작업은 저장된 최근 표본을 읽어 **지금의 상태**만 계산한다 — 밀린 항목을 한꺼번에 받아도 과거의 넘음·해소를 줄줄이 알리지 않는다. 관측 서버가 꺼져 있던 구간의 이벤트는 보내지 않는다.
- 지속 시간은 **측정 시각**으로 잰다(관측 횟수가 아니다). 판정 창 안의 표본이 기대 수의 절반에 못 미치면(결측) 그 규칙은 **판정을 미루고 상태를 그대로 둔다** — 결측을 넘음으로도 해소로도 보지 않는다.
- **끊김**: 알아야 할 서버 이름을 설정(`METRICS_EXPECTED_SERVERS`)으로 준다. 한 번도 보내지 않은 서버 · 하루 넘게 끊긴 서버도 판정하고 `GET /metrics/latest` 에 "수신 없음"으로 나온다. 판정은 수신 시각 기준.
- **디스크는 세 단계**: 정상 → 경고(85% 이상 연속 2회) → 위험(95% 이상 연속 2회). 위험 → 경고(92% 아래 연속 2회 — "위험 해소, 경고 유지" 1회 알림) → 정상(82% 아래 연속 2회). 단계가 바뀔 때마다 1회, 같은 단계가 이어지면 1시간마다.
- **상태 변경과 보낼 알림은 한 트랜잭션에 기록한다**(상태 표 + 보낼 알림 표). 보내는 일은 그 표를 읽어 하고, 성공하면 표시한다 — 보낸 직후 죽어도 다시 보내지 않도록 알림마다 고유 키를 두고, 못 보낸 것은 다음 바퀴에 다시 보낸다.
- **한 번에 한 인스턴스만 판정한다**: 자리 전환 중 두 인스턴스가 함께 떠 있어도 판정·발송 작업은 DB 의 잠금을 얻은 쪽만 돈다.
- **빠른 재발생(알려진 한계)**: 같은 규칙이 10분 안에 해소됐다 다시 넘으면 알림 서버가 같은 key 를 억제해 두 번째 "넘음"은 발송되지 않는다. 어드민 화면에는 보인다 — 수용.
- **재시작 반복**은 컨테이너 ID 별 증가량으로 센다. 컨테이너가 새로 만들어지면(배포) 새 기준이다 — 배포가 재시작으로 세지지 않는다.

### 11.5 계열 이름과 자리 전환
- 원본은 컨테이너의 실제 이름과 ID 로 저장한다. 조회의 `name` 은 자리 이름(`-blue` · `-green`)을 뗀 이름이고, 같은 시각에 두 자리가 함께 있으면 **합**(CPU · 메모리)으로 본다(전환 중 잠깐 두 배로 보이는 것이 실제 사용량이다).
- **연관 로그의 서버 찾기**: `GET /metrics/containers?server=&at=` 에 시각을 주면 그 시각 앞뒤 5분에 보인 컨테이너만 답한다. 어드민은 로그 시각으로 물어 그때 그 서비스가 있던 서버를 고른다(지금의 위치로 짐작하지 않는다).

### 11.6 조회
- `step_ms` = 기간을 500으로 나눈 값을 30초 단위로 올린 것(최소 30초). 7일보다 오래된 구간이 들어 있으면 최소 5분. 응답의 `source` 는 `raw` · `rollup` · `mixed`(경계를 걸친 요청). 점은 500개를 넘지 않는다(경계 계산을 테스트로 고정).
