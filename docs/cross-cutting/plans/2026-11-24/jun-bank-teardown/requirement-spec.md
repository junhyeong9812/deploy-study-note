- **① 목표·대상**: 더 쓰지 않는 다른 프로젝트 jun-bank 를 집 서버 세 대(`.9`·`.158`·`.164`)와 엣지에서 지운다 — 컨테이너 5, `jun-agent` 프로세스 2, 볼륨 `jun-deploy-mysql-data`, 이미지 `ghcr.io/jun-bank/*`, 폴더 `~/jun-deploy`(세 서버)·`~/jun-bank`(`.9`), 엣지의 `deploy.junproject.xyz`·`bank.junproject.xyz` 설정 둘.
- **② 경계·불변식**: 이 프로젝트(study-note 배포 시스템)의 컨테이너·볼륨·이미지·폴더·엣지 설정은 하나도 바뀌지 않는다. 지우는 것은 이름으로 하나씩 지정한다(패턴으로 뭉뚱그려 지우지 않는다 — `docker system prune` · `rm -rf ~/jun*` 금지). 엣지는 `nginx -t` 통과 뒤에만 다시 읽힌다.
- **③ 기준소스**: 서버의 현재 상태(삭제 직전 다시 조회) · `project-deploy-data/network/routing.md`.
- **④ 금지영역**: 이름이 비슷한 다른 것(`seatlab-*` 이미지, `readlog` 백업 crontab, `llm-boot.sh`) · 엣지의 인증서와 자동 갱신 · 공유기 포트 연결 · sudo 가 필요한 일(안내만 한다).
- **⑤ 검증 방법**: 삭제 뒤 세 서버에서 남은 컨테이너·볼륨·이미지·13000대 포트·폴더를 다시 조회해 대상이 0건이고, 이 프로젝트의 컨테이너 수와 헬스가 삭제 전과 같은지 본다. 알림 서버의 감시 대상 10개가 전부 UP 인지 본다. 엣지는 `www`·`admin` 이 200 그대로인지 본다.
- **⑥ stakes**: 높음(되돌릴 수 없는 삭제 — DB 데이터·폴더). 삭제 직전에 대상 이름·경로를 다시 확인한다.
- **자율성**: auto.
- **load-bearing 가정**: jun-bank 의 것과 이 프로젝트의 것은 컨테이너 이름·compose 프로젝트·폴더가 겹치지 않는다(조사에서 확인: jun-bank 는 `~/jun-deploy` 아래의 compose 프로젝트 `gateway`·`core-green`·`settlement`·`ledger` 와 단독 컨테이너 `jun-deploy-mysql`).
