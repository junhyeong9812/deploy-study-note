# requirement-spec — 알림 서버 (서비스 생존 감시 · 발송 · 엣지 감시자)

> 2026-11-20. 대상 repo: `alert`(신규, 공개) · `ci-cd`(서비스 목록에 alert 추가, 배포 실패·자리 방치 이벤트 발송) · `backend`(의존 서비스 헬스 그룹) · `front`(이벤트 접수·헬스 중계) · 엣지(감시 스크립트 + 예약 작업).
> 로드맵(`NEXT.md`) N4. 뒤따르는 작업: 관측 서버(로그) → 어드민 뼈대 → 자원 지표 → 방문 추적.

## 0. 요구사항 원문
- 사용자(11-19~20): "문제가 있을 때 알림을 보내는 알림 서버를 하나 두는게 맞겠네" · "알림서버에 문제가 있으면 어떻게 처리 … 이중으로 띄워서 상호보완?" → 집 밖 감시자 + 하루 한 번 메시지로 합의("그렇게 처리하자").
- 구조 합의: Kotlin · 서버는 관측 서버와 알림 서버 둘 · 어드민 백엔드 없음(화면이 조립) · 어드민 로그인은 ID/PW · 서버 간 메시지 통로는 Redis Stream(로그·방문 기록).
- 선택 답: 감시 대상 = 서비스 생존 + 의존 서비스 + 배포 시스템·배포 결과 + 밖에서 본 사이트 / 알림 조건 = 3번 연속 실패 / 규칙 = 파일로 시작(어드민은 나중) / 채널 = 디스코드 기본, 실패 시 슬랙 → 메일.
- 관측 신호: `.164` LLM이 2주간 꺼져 있었는데 사용자 제보로 앎 · 배포 실패는 GitHub 메일뿐 · 엣지→집 연결이 약 2분씩 끊기는 일이 이틀간 6회, 그중 1회는 배포 접수 실패로 이어짐 · 11-20 llm 구 자리 방치는 agent 로그에만 남음.

## ① 목표·대상
서비스가 죽거나, 의존 서비스가 안 되거나, 배포가 실패하거나, 밖에서 사이트가 안 보이면 **몇 분 안에 디스코드로 알림이 온다**(디스코드가 안 되면 슬랙 → 메일). 알림 서버 자신이 죽으면 집 밖(엣지)의 감시자가 알린다. 매일 아침 요약이 온다 — 오지 않으면 그것이 신호다.

## ② 경계·불변식
- **독립성**: 알림 서버는 관측 서버·PostgreSQL·Redis 없이 동작한다. 감시 대상 어느 하나가 죽어도 알림 서버의 확인 주기와 발송이 멈추지 않는다(대상별 시간 제한 5초, 대상끼리 서로 기다리지 않음).
- **감시 대상(설정 파일 `monitors.yml`, repo 소유, 비밀값·IP 없음 — 주소는 env 참조)**
  - 서비스 생존: front `/` · backend `/actuator/health` · llm `/health`
  - 의존 서비스: backend `/api/health/dependencies`(ES·Redis·임베딩 — backend에 신설하는 별도 경로. actuator 헬스에 지표를 더하면 기본 헬스 합산이 바뀌므로 쓰지 않는다) · llm `/health`의 `model_missing`·`ollama_unreachable` 구분
  - 배포 시스템: ci-cd master `/health` · agent 3대 `/health`
- **판정**: 30초 주기. **3번 연속 실패 → DOWN 알림 1회**. 복구되면 복구 알림(끊긴 시간 포함). DOWN이 이어지면 1시간마다 다시 알림. 한 번의 실패·시간 초과로는 알리지 않는다. 대상이 한꺼번에 여럿 죽으면(서버 한 대 다운) 알림 하나로 묶는다(같은 주기에 DOWN이 된 것끼리).
- **이벤트 접수** `POST /events`(서버 간 비밀값 `X-Alert-Secret`): 다른 서버가 알릴 일을 보낸다 — `{source, kind, severity, key, title, detail}`. 같은 `key`는 10분 안에 한 번만 발송(반복 억제), 접수는 전부 기록.
  - ci-cd master: 배포가 `failed`로 끝나면 발송(서비스·단계·출력 끝부분). 발송 실패는 배포 결과에 영향 없음(로그만).
  - ci-cd agent: 자리 정지 보류·되돌림 미확인·활성 파일 복원 실패 때 발송(두 자리가 남았을 수 있는 상황).
- **발송**: 디스코드 → (실패 시) 슬랙 → (실패 시) 메일. 채널마다 시간 제한 5초·재시도 2회. 세 채널 모두 실패하면 error 로그 + 다음 주기에 다시 시도(조용히 버리지 않는다). 채널 연결 정보는 서버 `.env`에만 둔다(repo·로그에 값이 나오지 않게).
- **하루 한 번 요약**(09:00 KST, 디스코드 + 메일): 대상별 현재 상태, 지난 24시간의 DOWN 횟수·합계 시간, 접수한 이벤트 수, 발송 실패 수.
- **기록**: 상태 변화·이벤트·발송 결과를 SQLite 파일(호스트 볼륨)에 남긴다. 30일 지난 행은 지운다. 조회 API `GET /incidents`·`GET /monitors`(서버 간 비밀값) — 어드민 화면이 나중에 쓴다. 기록 쓰기에 실패해도 감시와 발송은 계속한다(기록은 부가 기능).
- **재시작**: 재시작 직후에는 대상 상태를 "모름"에서 시작해 3번 확인 전에는 알리지 않는다. 직전에 DOWN이던 대상이 재시작 뒤에도 DOWN이면 다시 알리지 않고 이어 간다(SQLite의 마지막 상태로 판단).
- **엣지 감시자**(집 밖, 셸 스크립트 + 1분 예약 작업): ①사이트(`/`) ②알림 서버 헬스(front가 중계하는 경로)를 엣지에서 집으로 직접 확인. 3분 연속 실패 → 엣지가 디스코드 웹훅을 직접 호출. 복구되면 끊긴 시간을 알리고, 알림 서버에 이벤트로도 보낸다(front 중계 경유). 2분 미만의 끊김은 알리지 않고 엣지의 로그 파일에 시각·길이만 남긴다(끊김 원인 조사용).
- **front 중계**: `GET /api/ops/alert-health`(알림 서버 헬스) · `POST /api/ops/alert-events`(이벤트 접수, 비밀값 패스스루) — 기존 배포 중계와 같은 방식.
- **배포**: 알림 서버도 ci-cd 파이프라인으로 배포한다(테스트 단계·blue/green). `.9`에 둔다. ci-cd의 서비스 목록에 `alert` 추가.
- **알림 서버 자신의 배포 중**에는 구 자리가 감시를 계속하고, 전환 뒤 새 자리가 이어받는다. 겹치는 동안 같은 알림이 두 번 가지 않게 **감시·발송·요약은 프록시(nginx)가 실제로 요청을 보내는 자리 하나만** 한다 — 각 자리가 매 바퀴 프록시의 `X-Deploy-Slot`을 보고 판단한다. 정리 알림을 받은 구 자리는 곧바로 내려놓되, 프록시가 여전히 그 자리로 보내면(전환 되돌림·정지 보류) 다음 바퀴에 다시 맡는다. 새 자리는 기록에서 직전 DOWN 상태를 이어받고 나머지는 "모름"에서 시작한다. 사건(`/events`)은 받은 자리가 처리한다. *(11-20 리뷰 반영으로 고침 — 원문: "정리 알림을 받은 구 자리는 발송을 멈춘다". 원문대로면 정지가 보류된 활성 자리가 감시를 끈 채 헬스만 정상으로 남는다. log 리뷰 ledger 참조. **사용자 확인 대기**)*

## ③ 기준소스
backend `application.yml`(actuator는 `health`만 노출, 상세 없음 — 실측 `{"status":"UP"}`) · llm `wrapper/src/app/api.py`의 `/health`(200/503 + status 문자열) · ci-cd `internal/master/master.go`·`internal/agent/{agent.go,bluegreen.go}`(서비스 목록 고정 열거 `front·backend·llm`, 실패 지점) · front `src/features/deploy/lib/relay.ts`(중계 방식) · 엣지 `project-deploy-data/edge/`(conf·런북) · 실측(11-20: `.9` 여유 메모리 13GB, ES·임베딩은 compose 내부에만 열림, Redis는 LAN 6379).

## ④ 금지영역
자원 임계값·로그 오류율 알림(관측 서버 작업) · 어드민 화면·규칙 편집 API · 알림 서버 이중화 · PostgreSQL·Redis 의존 · 문자·전화 발송 · 엣지 nginx conf 변경(스크립트와 예약 작업만 추가) · 감시 대상 서비스의 동작 변경(backend는 헬스 그룹 추가만, 기존 `/actuator/health` 응답·배포 헬스 판정 무변경) · 다른 프로젝트 컨테이너(jun-bank·seatlab) 감시.

## ⑤ 검증 방법
- 단위(alert): 3번 연속 실패에서만 DOWN · 복구 알림에 끊긴 시간 · 1시간 재알림 · 같은 주기 다중 DOWN 묶음 · 대상 하나가 5초를 끌어도 다른 대상 확인이 밀리지 않음 · 채널 폴백 순서와 전부 실패 시 재시도 · 이벤트 반복 억제(같은 key 10분) · 인증 없는 접수 401 · 재시작 뒤 중복 알림 없음 · 기록 쓰기 실패에도 발송 · 설정 파일 오류면 기동 실패(조용한 기본값 금지).
- 단위(ci-cd·backend·front): 배포 실패 시 이벤트 발송·발송 실패 무해 / 헬스 그룹이 ES·임베딩 다운을 반영하되 기존 헬스는 불변 / 중계 2종.
- 실행(서버): ① llm 래퍼를 잠깐 내려 약 1분 30초 뒤 DOWN 알림, 올리면 복구 알림 ② 테스트가 깨진 커밋 대신 **ci-cd에 없는 서비스로 접수하지 않고**, 헬스 주소를 잠시 틀리게 한 배포로 실패 알림 확인(11-20 실험 방식) ③ 디스코드 웹훅을 일부러 틀리게 해 슬랙으로 넘어가는지 ④ 알림 서버를 내리고 3분 뒤 엣지가 알리는지 ⑤ 다음 날 09:00 요약 수신.
- 반증: 알림 서버가 감시 대상 하나 때문에 멈추지 않나? 배포 중 흔들림에 울리지 않나(무중단이므로 0건이어야 한다)? `.9` 랜 끊김(37분마다 20초)에 울리지 않나? 알림이 와야 할 때 세 채널이 모두 실패하면 어디에 남나?
- 리뷰: 중간 — 듀얼 1패스 + post-fix 재점검.

## ⑥ stakes: 중간
새 서비스(외부 API 호출·재시도·시간 제한·동시 확인) + 세 repo의 작은 변경 + 엣지 예약 작업. 데이터 변경 없음. 알림 서버가 잘못돼도 서비스에는 영향이 없고(이벤트 발송은 무해 실패), repo별 revert로 복구된다. 잘못된 알림(오탐·누락)이 주된 위험.

## 자율성
auto 제안. **새 공개 저장소 생성**, 이슈·push·PR·병합, `.9` 배포 설정(.env — 채널 값은 사용자가 직접 입력), **엣지 서버의 스크립트·예약 작업 추가**는 각각 확인.

## 사용자가 준비할 것 (비밀값 — 서버 `.env`에 직접 입력)
디스코드 웹훅 URL · 슬랙 웹훅 URL · Gmail 주소와 앱 비밀번호 · 알림을 받을 메일 주소. 엣지에는 디스코드 웹훅 URL 하나.

1. 엣지에서 집의 front 포트로 직접 `curl`이 된다(엣지 nginx가 쓰는 그 경로) — 감시 스크립트의 전제.
2. ~~헬스 그룹~~ → 별도 경로로 구현해 기본 `/actuator/health`와 compose·배포의 헬스 판정이 구조상 바뀌지 않는다(11-20 설계 변경 — log 참조).
