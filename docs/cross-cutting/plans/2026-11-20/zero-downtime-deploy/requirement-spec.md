# requirement-spec — 무중단 배포 (blue/green + 서버별 nginx)

> 2026-11-20. 대상 repo: `ci-cd`(agent의 CD 단계) · `backend` · `front` · `llm`(compose·nginx 설정, llm·backend는 대기열 인계 코드 포함). 전제 작업: `2026-11-19/deploy-pipeline-reliability/`(CI는 이미지 빌드, CD는 교체만).

## 0. 요구사항 원문
- 사용자(11-19): "무중단 배포를 위한 설계도 추가해야" · "채팅 스트림은 최대 2개니깐 그 2개가 끝나고, 그 뒤 큐의 응답은 다음 서버로 넘겨주는 형태"
- 선택 답(11-20): 전환 장치 = 서버마다 nginx / 구 버전 대기 = 최대 3분 / llm 대기열 = 새 버전으로 넘김 / 진행 = 한 명세, 서비스별 단계(backend → front → llm)
- 실측(11-20): 여유 메모리 `.9` 13GB · `.158` 9.8GB · `.164` 30GB(앱 한 벌 backend 407MB·front 114MB·llm 35MB). 지금 교체 4~8초 동안 요청 실패. 세 서비스 모두 compose에 컨테이너 이름·호스트 포트 고정. backend에 주기 작업 없음(sync는 요청으로만 동작).

## ① 목표·대상
배포 중에도 요청이 실패하지 않는다. 새 버전을 옆에 띄워 헬스를 확인한 뒤 nginx가 새 요청을 그쪽으로 넘기고, 구 버전은 남은 연결을 끝낸 뒤(최대 3분) 내려간다. 새 버전이 헬스에 실패하면 구 버전이 계속 서비스한다.

## ② 경계·불변식
- **구성**: 서버마다 `nginx` + 앱 두 자리(`blue`·`green`). 지금의 외부 포트(front 11000 · backend 8090 · llm 8000)는 nginx가 받는다 — 호출하는 쪽(엣지·front·backend)의 주소는 바뀌지 않는다. 앱 두 자리는 각각 `127.0.0.1`에만 열린 포트를 갖는다(agent의 헬스 확인용).
- **평소에는 한 벌만 뜬다.** 두 벌이 같이 도는 것은 배포 중(전환 전 헬스 확인 ~ 구 버전 종료)뿐이다.
- **전환 순서**(agent CD): 비활성 자리에 새 이미지 기동 → 그 자리의 헬스 통과 → nginx 대상 변경(`nginx -t` 통과 후 reload) → 외부 포트로 헬스 재확인 → 여기서 배포는 `succeeded`. 구 버전 정리는 그 뒤의 뒷일이다.
- **전환 전 실패 = 운영 무변경.** 새 자리 기동·헬스가 실패하면 nginx를 건드리지 않고 새 자리만 내린다(`cd_up`·`cd_health`). nginx 설정 검사가 실패하면 이전 설정으로 되돌리고 새 자리를 내린다. reload를 시도한 뒤의 실패는 이전 설정으로 되돌리되, 새 자리에 이미 들어간 연결이 끝날 때까지(최대 3분) 새 자리를 둔 뒤 내린다(`cd_switch` — 실패 단계 추가).
- **구 버전 정리**: 전환 뒤 구 버전에 남은 연결이 모두 끝나면 바로, 아니면 **3분**에 내린다(상한 있는 대기). 정리 중에 같은 서비스의 다음 CD가 오면 정리가 끝날 때까지 기다린 뒤 진행한다. 정리 실패(구 버전이 안 내려감)는 배포 결과를 바꾸지 않되 로그에 남기고, 다음 CD가 시작 전에 다시 내린다 — 거기서도 못 내리면 그 CD는 중단한다. agent가 재시작되면 실제 활성 자리의 반대쪽을 정리한다(두 벌 방치 금지).
- **요청 실패 0**: 배포 중 새 연결은 항상 헬스를 통과한 자리로만 간다. 전환 시점에 열려 있던 연결(SSE·NDJSON 스트림 포함)은 구 버전에서 끝까지 간다(3분 안).
- **스트림 통과**: nginx는 응답을 버퍼링하지 않는다(`proxy_buffering off`), 읽기 제한은 200초(백엔드 유휴 감시 150초·엣지 60초보다 길게). 기존 `X-Accel-Buffering`·keep-alive 15초·대기 재전송 10초 계약 무변경.
- **활성 자리 판정 = nginx가 실제로 보내는 자리**(응답의 `X-Deploy-Slot` 헤더). nginx가 읽는 대상 파일(서버의 배포 디렉토리 안, git 미추적)은 원하는 자리를 전하는 수단이다. 둘이 다르면 실제를 따라 파일을 고친 뒤 진행하고, 파일이 없거나 외부 포트가 응답하지 않으면 CD를 거절한다(추측 전환 금지). 전환 성공도 "외부 헬스 200"이 아니라 "새 자리가 응답함"으로 판정한다. — 설계 선검증 반영(11-20): 파일만 정본이면 파일을 바꾼 직후 중단되거나 reload가 적용되지 않았을 때 운영 중인 자리를 내릴 수 있다.
- **llm 대기열 인계**: 전환 뒤 agent가 구 버전에 "정리 시작"을 알린다. 구 버전은 **생성 중인 건은 끝까지** 하고, **아직 시작하지 않은 대기자**에게는 `{"type":"retry"}` 이벤트를 보낸 뒤 그 연결을 닫는다. backend는 `start` 전에 `retry`를 받으면 같은 질문을 다시 보낸다(한 요청당 최대 2회, 넘으면 `upstream` 오류). 브라우저에는 `retry`를 내보내지 않는다 — 화면은 "대기 중"이 이어진다. 구 버전은 대기자를 **순번대로 간격을 두고** 내보내 새 버전에서도 순서가 대체로 유지되게 한다(완전한 FIFO 보장은 아님 — 명시).
  - 전환 중 GPU 동시 생성은 Ollama(`NUM_PARALLEL=2`)가 2건으로 제한한다. 두 래퍼가 각각 2건까지 `start`를 낼 수 있어, 그동안 최대 2건은 `start` 뒤 첫 토큰이 늦어질 수 있다.
  - 정리 알림 경로는 구 버전의 `127.0.0.1` 포트로만 받는다. nginx는 그 경로를 외부로 넘기지 않는다.
- **전환 중 sync 겹침**: backend sync는 공유 볼륨의 git 작업이다. 전환 직전에 들어온 sync가 구 버전에서 도는 동안 새 버전이 또 sync를 받는 겹침은 막지 않는다(sync는 드물고 다음 sync가 바로잡는다 — 알려진 한계로 기록).
- **이미지·원복 기준**: 운영 중인 버전 = 활성 자리 컨테이너의 이미지 태그. CI 실패 시 원복 기준과 이미지 5개 보존은 이 기준으로 동작한다.
- **시간 예산**: CD = 기동 2분 + 헬스 90초 + 전환 30초 + (앞선 정리 대기 최대 3분 + 자리 정지 여유 70초). 워크플로 조회 상한을 **25분**으로 올린다(작업 중 대기 3 + CI 11.5 + CD 8 + 여유). 구 버전 정리는 `succeeded` 뒤에 돌므로 예산 밖이다.
- **수동 조작 문서화**: 서버에서 손으로 올리거나 되돌리는 명령(활성 자리 확인, 전환, 구 버전 종료)을 ci-cd README에 적는다.
- 비밀값·IP는 repo에 넣지 않는다. 엣지 nginx는 건드리지 않는다.

## ⑤ 검증 방법
- 단위(ci-cd): 전환 순서(기동→헬스→설정→reload→재확인) · 새 자리 헬스 실패 시 nginx 무변경·새 자리 종료 · 설정 검사 실패 시 이전 설정 복원 · 활성 파일 없으면 거절 · 정리 중 다음 CD는 대기 · 운영 버전 판정이 활성 자리 기준. llm: 정리 시작 시 대기자에게 `retry`·생성 중 건은 완료·순번 순서로 내보냄. backend: `retry` 수신 시 재요청, 3번째는 오류, `start` 뒤의 `retry`는 재요청하지 않음.
- 실행(서버, 서비스별): **배포 내내 초당 여러 번 요청을 보내 실패 0건**(backend 검색·front 페이지·llm 헬스). 이전 방식과 같은 방법으로 비교 측정. 배포 뒤 컨테이너가 한 벌만 남는지. 새 버전 헬스를 일부러 실패시켜 구 버전이 계속 서비스하는지.
- 실행(채팅): 생성 중인 답변이 있는 상태에서 backend·front·llm을 각각 배포 → 답변이 끊기지 않고 끝나는지. llm 배포 시 대기 중이던 질문이 새 버전에서 이어져 답을 받는지.
- 반증: reload 뒤에도 구 버전으로 새 요청이 가지 않나? 3분 뒤에도 안 끝난 연결이 구 버전을 붙잡지 않나? 서버 재부팅 뒤 한 벌만, 올바른 자리가 뜨나? nginx 컨테이너 자체가 죽으면 어떻게 보이나?
- 리뷰: 높음 — 듀얼 리뷰 루프(≤3) + 설계 선검증(새 동작 불변식: 전환 전 실패 = 운영 무변경, 구 버전 정리 상한, 대기열 인계) + blind 테스트 워커.

## ⑥ stakes: 높음
세 서비스의 기동 방식·포트 소유가 바뀌고(운영 토폴로지 변경), 처음 적용할 때 서버마다 수동 전환이 필요하다. 동시성(두 벌 공존·대기열 인계)과 llm↔backend 스트림 계약 추가(`retry`)가 들어간다. 되돌리기는 repo revert + 서버에서 이전 compose로 재기동(서비스당 수 초 중단).

## 자율성
auto 제안. 이슈·push·PR·병합과 **서버별 최초 전환**(서비스당 수 초 중단이 한 번 생긴다)은 각각 확인.

## load-bearing 가정 (착수 직후 실증)
1. nginx를 reload하면 그 시점에 열려 있던 스트림 연결은 구 버전에서 끊기지 않고 이어지고, 새 연결은 새 대상으로만 간다(로컬에서 스트림을 물린 채 reload해 실측).
2. 남은 연결 수를 nginx에서 알아낼 수 있다(종료 중인 worker 프로세스 유무) — 안 되면 "3분 고정 대기"로 단순화하고 보고.
