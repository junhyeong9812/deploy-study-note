## 1. nginx reload 와 열린 스트림 (로컬)

nginx 1.27 뒤에 스트림 서버 두 개(blue·green)를 두고, 12초짜리와 40초짜리 스트림을 연 채 대상을 green 으로 바꿔 reload 했습니다. `worker_shutdown_timeout` 은 20초로 두었습니다.

| 확인 | 결과 |
|---|---|
| reload 직후 새 요청 10건 | 10건 모두 green |
| 12초 스트림 | blue 에서 12줄 전부 수신 |
| 남은 연결을 알 수 있는가 | 연결이 남은 동안 `ps` 에 `shutting down` worker 1개, 끝나면 0개 |
| 상한이 걸리는가 | 40초 스트림이 약 21초(24줄)에서 끊김 |

운영 설정의 상한은 180초입니다.

실제 agent 이미지와 실제 nginx 설정, 자리 두 개짜리 스트림 서버로 `POST /agent/cd` 를 호출했습니다. 구성을 고칠 때마다 다시 돌렸습니다.

| 구성 | 전환 시간 | 부하 | 스트림 | 정리 뒤 |

| 첫 구현 | 4.4초 | 189건 실패 0 | 15줄 완주(구 버전) | 한 벌 |
| 자리에 profiles, 설정 디렉토리 마운트 | 4.3초 | 218건 실패 0 | 10줄 완주 | 한 벌 |

## 3. 실패 경로 (로컬, 부하 유지)

| 상황 | 결과 단계 | 운영 |
|---|---|---|
| 없는 이미지로 배포 | `cd_up` | 구 버전 그대로 |
| 대상 자리 템플릿의 nginx 문법 오류 | `cd_switch` | 구 버전 그대로, 활성 파일 복원 |
| 대상 자리 헬스 실패 | `cd_health` | 구 버전 그대로 |
| nginx 본 설정 원본이 깨진 커밋 | `cd_switch` | 구 버전 그대로, 운영 사본 복원(`nginx -t` 통과) |

첫 세 실험 내내 1,022건, 네 번째를 포함한 연속 배포 내내 309건을 보냈고 실패는 0건이었습니다.

## 5. 죽은 앱에서 고치는 배포 (로컬)

운영 중인 green 을 강제 종료하자 nginx 가 502 와 `X-Deploy-Slot: green` 을 돌려줬습니다. 그 상태에서 배포를 호출하자 blue 로 전환됐습니다. 응답이 200 이 아니어도 자리 표식으로 판정하기 때문입니다.

## 6. backend 최초 전환 (서버 `.158`)

포트 주인을 앱에서 nginx 로 바꾸는 작업이라 한 번의 중단이 필요합니다. 중단을 줄이려고 새 자리(blue)를 먼저 띄워 헬스를 확인한 뒤 포트만 넘겼습니다.

```
blue 기동 → 헬스 200 (약 6초, 기존 컨테이너는 계속 서비스)
08:27:02.840  기존 컨테이너 정지 시작
08:27:08.496  nginx 기동 완료
```

- 중단 5.4초, 그동안 요청 46건 실패.
- ES·Redis·embedding 컨테이너의 생성 시각은 그대로였습니다.
- 첫 시도는 실패했습니다. 서버의 `deploy/` 폴더가 root 소유라 활성 폴더를 만들 권한이 없었습니다. 아무것도 바뀌지 않은 채 멈췄고, agent 컨테이너를 통해 폴더를 만들어 다시 진행했습니다.

## 7. backend 무중단 배포 (서버)

최초 전환 뒤 워크플로를 재실행했습니다(같은 커밋, blue → green).

```
08:28:41Z agent ci start
08:28:44Z agent ci ok (3.0초)
08:28:44Z agent cd start
08:28:53Z agent cd ok (8.3초)
08:28:54Z 자리 정리 완료 app-blue
```

| 요청 | 결과 |
|---|---|
| 트리 조회 `/api/tree` (150초) | 579건 실패 0 |
| 검색 `/api/search` (150초) | 102건 성공, 1건 실패 |

검색의 실패 1건은 08:28:33Z 로, 배포가 시작되기 8초 전입니다. 측정 쪽 제한 3초를 넘긴 느린 응답이었습니다. 제한을 10초로 늘린 8번 실험에서는 검색 실패가 없었습니다.

배포 뒤 응답 자리는 green, 활성 파일도 green, 떠 있는 앱 컨테이너는 green 하나였습니다.

## 8. 새 자리 헬스 실패 (서버)

agent 의 blue 헬스 주소를 닫힌 포트로 바꾼 뒤 배포했습니다(끝난 뒤 원래대로 되돌림).

```
status: cd_running (8회)
status: failed
배포 실패 — 단계: cd_health
health 미도달: Get "http://127.0.0.1:1/actuator/health": connect: connection refused
```

- 응답 자리는 계속 green, 활성 파일도 green, 떠 있는 앱은 green 하나(새로 띄운 blue 는 정지).
- 200초 동안 트리 조회 775건·검색 140건, 실패 0건.
- 이 실험의 첫 시도는 다른 이유로 실패했습니다. 워크플로의 접수가 엣지에서 504 를 5번 연속 받아 "접수 실패 5회"로 끝났습니다(08:31Z 전후). 엣지에서 집으로 약 2분간 연결이 안 되는 현상이고, 재시도 5회로는 넘기지 못했습니다.

## 9. agent 재기동 뒤 정리 (서버)

8번 실험에서 agent 를 네 번 재기동했습니다. 매번 기동 직후 로그에 `자리 정리 완료 app-blue` 가 찍혔고 앱은 green 하나만 떠 있었습니다. 서버 전체 재부팅은 하지 않았습니다.

## 10. 지금 방식의 배포 중 실패 (서버)

front 와 llm 은 아직 단일 컨테이너 방식입니다. 워크플로 상한을 올리는 PR 의 배포에서 같은 방법으로 쟀습니다.

| 서비스 | 요청 | 실패 | 실패 구간 |
|---|---|---|---|
| llm `/health` | 1,206건 | 5건 | 08:42:59.400 ~ 59.892 (약 0.5초) |
| front `/` | 449건 | 3건 | 08:46:43.818 ~ 44.067 (약 0.25초) |

두 서비스는 컨테이너가 빨리 떠서 실패 구간이 1초 미만입니다. backend 는 최초 전환 때 잰 5.4초가 비슷한 조건(정지 후 기동)의 수치입니다.

## 아직 확인하지 않은 것

- 서버 전체 재부팅 뒤 한 벌만 올바른 자리로 뜨는지.
- 생성 중인 채팅 답변이 있는 상태에서의 배포(front·llm 을 옮긴 뒤 함께 확인).
- front·llm 의 무중단 전환과 llm 대기열 인계(다음 단계).
- 되돌림이 실제로 일어나는 경로(reload 뒤 실패)의 서버 실측 — 단위 테스트와 로컬 실험으로만 확인.
