## 1. nginx reload 와 열린 스트림 (로컬)

nginx 1.27 뒤에 스트림 서버 두 개(blue·green)를 두고, 12초짜리와 40초짜리 스트림을 연 채 대상을 green 으로 바꿔 reload 했습니다. `worker_shutdown_timeout` 은 20초로 두었습니다.

| 확인 | 결과 |
|---|---|
| reload 직후 새 요청 10건 | 10건 모두 green |
| 12초 스트림 | blue 에서 12줄 전부 수신 |
| 남은 연결을 알 수 있는가 | 연결이 남은 동안 `ps` 에 `shutting down` worker 1개, 끝나면 0개 |
| 상한이 걸리는가 | 40초 스트림이 약 21초(24줄)에서 끊김 |

운영 설정의 상한은 180초입니다.

## 6. backend 최초 전환 (서버 `.158`)

포트 주인을 앱에서 nginx 로 바꾸는 작업이라 한 번의 중단이 필요합니다. 중단을 줄이려고 새 자리(blue)를 먼저 띄워 헬스를 확인한 뒤 포트만 넘겼습니다.

```

08:27:02.840  기존 컨테이너 정지 시작
08:27:08.496  nginx 기동 완료
```

- 중단 5.4초, 그동안 요청 46건 실패.
- ES·Redis·embedding 컨테이너의 생성 시각은 그대로였습니다.
- 첫 시도는 실패했습니다. 서버의 `deploy/` 폴더가 root 소유라 활성 폴더를 만들 권한이 없었습니다. 아무것도 바뀌지 않은 채 멈췄고, agent 컨테이너를 통해 폴더를 만들어 다시 진행했습니다.

## 14. llm 전환과 실제 사이트 채팅 (서버 `.164`)

**최초 전환.** 10:28:04.4 ~ 04.9Z, 0.5초 중단, 요청 4건 실패. Ollama 컨테이너는 그대로였습니다.

**1차 채팅 실험 — 결함 발견.** 공개 사이트로 5초마다 질문 4건씩 걸면서 배포했습니다.

- 인계는 동작했습니다. 구 버전 로그에 `chat handed off: draining` 7건이 0.2초 간격으로 찍혔고, backend 로그에 `chat handed off by llm — resending (1/2)` 7건이 같은 순서로 찍혔습니다. `llm_unreachable` 이나 `upstream` 오류는 없었습니다.
- 헬스 요청 911건은 실패 0건이었습니다.
- 28건 중 18건이 `queue_full`·`queue_timeout` 으로 끝났는데, 이것은 배포 탓이 아니라 실험 부하가 대기열 용량(동시 2·대기 8·60초)을 넘겼기 때문입니다.
- **구 자리가 내려가지 않고 남았습니다.** agent 로그: `자리 정지 보류 wrapper-blue — nginx가 보내는 자리 "blue"`.

**원인.** nginx 는 reload 때 새 worker 를 먼저 띄운 뒤 구 worker 에 종료 신호를 보냅니다. 전환 성공 직후의 짧은 틈에는 `ps` 에 아직 `shutting down` 이 없고, 구 worker 가 요청을 한두 개 더 받습니다. agent 는 그 순간을 한 번 보고 "남은 연결 없음, 그런데 아직 구 자리가 응답 중"으로 판단해 정지를 보류했습니다. backend 와 front 에서는 같은 틈이 반대로 작용해 구 자리를 전환 1초 뒤에 내렸습니다(긴 스트림이 걸려 있었다면 끊겼을 상황).

**수정.** 전환 뒤 2초를 기다린 다음 남은 연결을 보고, 응답 자리 확인은 5번까지 다시 봅니다(ci-cd #15).

**2차 채팅 실험 — 수정 뒤.** 9초마다 질문 2건씩, 12건을 걸면서 배포했습니다(green → blue).

| 확인 | 결과 |
|---|---|
| 질문 12건 | 12건 모두 `done` (토큰 896~986) |
| 배포 시점에 대기 중이던 2건 | 구 버전이 `retry`, backend 가 다시 보내 새 버전에서 시작·완료 |
| 헬스 요청 | 1,152건 실패 0 |
| 구 자리 | 전환 2초 뒤 정리, 앱 한 벌만 남음 |

이 실험에서는 생성 중이던 두 건이 전환과 같은 초(10:40:29Z)에 끝났습니다. 그래서 "생성 중인 답이 구 버전에서 이어지는 동안 구 자리가 기다린다"는 서버에서 직접 보지 못했습니다(로컬 11번 실험에서는 확인).

**관찰.** 새 버전으로 넘어간 질문은 대기 시간 제한(60초)이 새 버전에서 처음부터 다시 셉니다. 1차 실험에서 12.7초에 건 질문이 85초에 `queue_timeout` 으로 끝났습니다.

## 아직 확인하지 않은 것

- 서버 전체 재부팅 뒤 한 벌만 올바른 자리로 뜨는지.
- 서버에서 생성 중인 답이 구 버전에서 이어지는 동안 구 자리가 기다리는지(로컬에서만 확인).
- 되돌림이 실제로 일어나는 경로(reload 뒤 실패)의 서버 실측 — 단위 테스트와 로컬 실험으로만 확인.
- front 전환 직후, 배포 전에 열려 있던 브라우저 화면의 동작(구 버전 스크립트 파일 요청).
