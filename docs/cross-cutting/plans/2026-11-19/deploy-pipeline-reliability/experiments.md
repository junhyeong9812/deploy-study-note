# 배포 파이프라인 실험 기록

2026-11-19~20에 실제 서버에서 한 실험을 모았습니다. 명세(`requirement-spec.md`)의 "검증 방법"에 적은 항목을 하나씩 확인한 기록입니다. 시각은 로그에 찍힌 UTC 그대로이고, 한국 시간은 9시간을 더하면 됩니다.

## 실험 환경

| 역할 | 서버 | 내용 |
|---|---|---|
| master | `.9` | 접수, CI→CD 진행, 이력 DB(`data/deploys.db`) |
| agent | `.9` · `.158` · `.164` | front · backend · llm 을 각각 담당 |
| 엣지 | 오라클 nginx | `www.junproject.xyz` → 집 → front(`:11000`) → master |

배포 한 건은 `접수 → ci_running(받기·테스트·이미지 빌드) → cd_running(교체·헬스) → succeeded 또는 failed` 순서로 진행됩니다.

## 결과 요약

| # | 확인하려는 것 | 결과 |
|---|---|---|
| 1 | 정상 배포가 끝까지 가고, 워크플로가 그때까지 기다린다 | 확인 |
| 2 | 테스트가 깨지면 빨간불이 뜨고 운영은 그대로다 | 확인 |

| 6 | 엣지를 거쳐 배포 상태를 조회할 수 있다 | 확인 |
| 7 | 접수가 끝내 실패하면 빨간불이 뜬다 | 가짜 서버로만 확인 |

## 1. 정상 배포

**방법.** 세 저장소에 PR 을 병합하고 워크플로 로그, master 이력, 서버의 컨테이너를 확인했습니다.

**결과.** master 이력 DB 에 남은 행입니다.

| 요청 번호 | 서비스 | 커밋 | 상태 | 테스트+빌드 | 교체 |
|---|---|---|---|---|---|
| gh-44537793912 | front | acbe1e7 | succeeded | 113.3초 | 4.3초 |
| gh-44539224565-1 | llm | c22e081 | succeeded | 8.0초 | 3.6초 |
| gh-44545272097-1 | backend | e66f4d3 | succeeded | 58.2초 | 8.3초 |
| gh-44551381707-1 | front | 7b7395c | succeeded | 63.9초 | 4.4초 |

새 워크플로의 로그는 세 저장소 모두 같은 모양이었습니다.

```
submit: http=202 {"data":{"request_id":"gh-44539224565-1","service":"llm","state":"accepted"},"success":true}
status: ci_running
status: cd_running
status: succeeded
```

배포 뒤 컨테이너는 커밋 번호가 붙은 이미지로 떠 있었습니다(예: `llm-wrapper:c22e0816f0ac…`). 서버의 소스 디렉토리도 같은 커밋이었습니다.

**테스트가 실제로 돌았는가.** `.164` 와 `.158` 에서 `docker build --target test` 를 다시 실행하자 테스트 단계가 `CACHED` 로 나왔습니다. 배포 중에 그 단계가 실제로 실행돼 캐시에 남았다는 뜻입니다.

## 2. 테스트가 깨진 커밋

이 실험만 main 에 흔적을 남깁니다. llm 저장소에 커밋 2개(`1663013`, `92dab17`)가 있습니다.

**방법.**
1. 실험 전 `.164` 의 llm 컨테이너 상태를 기록했습니다.
2. 항상 실패하는 테스트 하나를 llm 의 main 에 올렸습니다(`1663013`).

   ```python
   def test_deliberately_broken_for_pipeline_check():
       assert 1 == 2
   ```
3. 워크플로 결과, master 이력, 컨테이너, 서버 소스를 확인했습니다.
4. 그 테스트를 지우는 커밋을 올렸습니다(`92dab17`).

**결과.**

| 확인 항목 | 실험 전 | 깨진 커밋 배포 후 |
|---|---|---|
| 워크플로 | — | 실패(빨간불) |
| master 이력 | — | `failed`, 단계 `ci_test`, 6.9초 |
| 컨테이너 이미지 | `llm-wrapper:c22e081…` | `llm-wrapper:c22e081…` (그대로) |
| 컨테이너 생성 시각 | 2026-11-19T14:01:13Z | 2026-11-19T14:01:13Z (그대로) |
| 서버 소스 커밋 | c22e081 | c22e081 (되돌려짐) |
| 깨진 테스트 파일 | 없음 | 없음 |
| `/health` | 정상 | 정상 |

워크플로 로그에는 실패한 테스트 이름까지 나왔습니다.

```
status: ci_running
status: failed
::error::배포 실패 — 단계: ci_test
----- 출력 끝부분 -----
FAILED src/test/test_pipeline_failure_check.py::test_deliberately_broken_for_pipeline_check
1 failed, 45 passed, 1 warning in 2.98s
ERROR: failed to solve: process "/bin/sh -c python -m pytest -q -p no:cacheprovider" did not complete successfully: exit code: 1
```

agent 로그에도 교체(CD)를 시작한 기록이 없습니다.

```
01:21:28Z agent ci start llm sha=1663013…
01:21:35Z agent ci failed llm stage=ci_test 6880ms
```

되돌리는 커밋(`92dab17`)은 정상 배포됐습니다(테스트+빌드 2.0초, 교체 3.6초). 컨테이너가 `llm-wrapper:92dab17…` 로 바뀌었습니다.

**읽는 법.** 테스트 실패는 교체 전에 걸러지고, 운영 중인 컨테이너는 재시작조차 하지 않습니다. 서버의 소스도 agent 가 운영 중인 버전으로 되돌립니다.

## 4. 접수 재시도

일부러 만든 상황이 아니라 실험 중에 실제로 일어난 장애입니다.

- **기존 워크플로(재시도 없음).** front 첫 PR(#44)의 배포 호출이 13:52:41Z 에 엣지에서 504 를 받았는데 워크플로는 초록불로 끝났습니다. master 에는 접수 기록이 없었고 서버는 이전 커밋 그대로였습니다. 수동으로 재실행해야 했습니다.
- **새 워크플로.** front 워크플로 PR(#45)의 접수가 504 를 4번 연속 받고 5번째에 접수됐습니다.

  ```
  15:08:30Z submit: http=504
  15:09:00Z submit: http=504
  15:09:31Z submit: http=504
  15:10:01Z submit: http=504
  15:10:22Z submit: http=202
  ```
  그 뒤 배포는 정상으로 끝났습니다.

엣지 nginx 오류 로그의 같은 시각에 집으로의 연결 시간 초과가 4건 있습니다. `.9` 의 랜 링크 끊김 기록은 그 시각에 없습니다(마지막이 14:39Z). 랜선과는 다른 원인으로 약 2분간 연결이 안 된 것입니다. 지금 재시도(5회, 20초 간격)는 약 2분을 버티므로 이번에는 마지막 시도에서 넘겼습니다. 재시도 횟수는 그대로 두기로 했습니다(2026-11-20 결정).

## 5. master 재시작 뒤 이력

**방법.** 이력 DB 를 읽기 전용으로 조회하고, master 컨테이너를 재시작한 뒤 다시 조회했습니다.

**결과.** 재시작 전후 모두 4건이 같은 내용으로 남아 있었습니다. 진행 중인 배포가 없었으므로 "미완료 건을 실패로 닫는" 동작은 일어나지 않았습니다. 그 동작은 단위 테스트(`TestRestartClosesUnfinishedDeploymentsAndKeepsHistory`)로만 확인했습니다.

## 6. 엣지를 거친 상태 조회

front 에 추가한 `GET /api/deploy/<요청 번호>` 가 엣지를 거쳐 master 까지 닿는지 확인했습니다.

| 호출 | 응답 |
|---|---|
| 비밀값 없이 조회 | 401 `unauthorized` (master 가 거절) |
| 형식이 다른 번호(`a.b`) | 422 `invalid_request` (front 가 master 를 부르지 않고 거절) |
| 워크플로의 정상 조회 | 200, 상태 반환(1번 실험의 로그) |

## 7. 실제 서버에서 확인하지 않은 것

- **접수가 5번 모두 실패해 빨간불이 뜨는 경우.** 가짜 서버를 띄워 워크플로 스크립트만 실행해 종료 코드 1을 확인했습니다. 같은 방법으로 접수 거절, 조회 중 유실(404), 20분 시간 초과, 다른 커밋이 배포된 경우도 확인했습니다.
- **교체나 헬스체크가 실패하는 경우(`cd_up`, `cd_health`).** 단위 테스트로만 확인했습니다.
- **배포 도중 master 가 죽는 경우.** 단위 테스트로만 확인했습니다.
- **오래된 이미지 정리.** 서비스마다 커밋 태그 이미지가 아직 5개를 넘지 않아 지우는 동작이 실행된 적이 없습니다.
